# PhishShield General Implementation Report

Project title: AI-Powered Phishing Detection System for Email and Web Apps

This report summarizes how PhishShield was implemented in the current repository, based on the actual source code, model artifacts, executed notebook outputs, and `phishshield-roadmap-v4.md`. The notebooks were inspected from their saved cells and outputs only; they were not rerun.

## 1. Executive Summary

PhishShield was implemented as a hybrid phishing detection system for two input channels: email messages and web URLs. The system combines offline-trained machine learning models, deterministic security checks, external URL reputation services, and an AI-powered natural language classification layer. The project is delivered through three main software components:

| Component | Implementation role | Main technologies |
|---|---|---|
| ML training pipeline | Trains and evaluates URL and email Random Forest models, exports runtime artifacts | Python, pandas, scikit-learn, skl2onnx, joblib, matplotlib |
| Backend API | Authenticates users, runs detection layers, ensembles scores, stores scan history | FastAPI, SQLAlchemy, PostgreSQL, JWT, Groq, httpx, joblib |
| User interfaces | Dashboard for manual analysis and history; browser extension for page-level URL checks | React, TypeScript, Vite, Tailwind CSS, Chrome MV3, ONNX Runtime Web |

The implementation was effectively done in two major parts:

1. The offline ML and evaluation part, where URL and email phishing classifiers were trained, evaluated, exported, and documented through feature contracts.
2. The deployable application part, where the trained models were integrated into a FastAPI backend, a React dashboard, and a Chrome browser extension.

The key research contribution is not a single classifier but a multi-layer architecture. URL detection uses a URL-specific Random Forest model and reputation checks. Email detection uses a separate Email Random Forest model trained on email-message features. Both scan types can also use an AI/NLP layer that scores urgency, impersonation, credential harvesting, and social engineering intent.

The most important change introduced after earlier roadmap versions is the dedicated Email Random Forest layer. In older designs, email sender addresses could be passed into the URL model. The current v4 design and implementation correct that problem by using separate model contracts for URL inputs and email inputs.

## 3. System Architecture

PhishShield follows a shared-backend architecture. The dashboard and extension both send scan requests to a FastAPI backend. The backend validates requests, runs the appropriate detection pipeline, combines active layer scores into a final risk score, and returns a structured response containing a verdict and explainable reasons.

The dashboard supports authenticated manual scanning of:

- URLs.
- Pasted email content.
- Uploaded `.eml` files.

The extension supports automatic URL scanning when a browser tab finishes loading. It extracts client-side features, attempts local ONNX inference, calls the backend for server-side URL analysis, merges both results, updates the browser badge, and injects a warning banner for suspicious or phishing pages.

The current architecture can be summarized as:

```text
React Dashboard                 Chrome Extension
      |                                |
      | /api/v1/analyze/url            | local Tier 1+2 features
      | /api/v1/analyze/email          | optional ONNX Model A
      | /api/v1/analyze/email/upload   | /api/v1/analyze/extension/url
      |                                |
      +--------------+-----------------+
                     |
              FastAPI Backend
                     |
        +------------+-------------+
        |                          |
   URL Pipeline              Email Pipeline
        |                          |
   URL RF Model              Email RF Model
   Google Safe Browsing      NLP Layer
   URLhaus                   Header Analyzer
   WHOIS/Tier 3              SPF/DKIM/DMARC
   NLP Layer                 EML Parser
        |                          |
        +------------+-------------+
                     |
              Ensemble Scoring
                     |
             PostgreSQL Database
```

## 4. Backend Implementation

The backend is implemented with FastAPI. The application entry point is `backend/api/app.py`, while `backend/main.py` runs the app locally with Uvicorn.

The API is mounted under versioned route prefixes:

| Route | Authentication | Purpose |
|---|---:|---|
| `POST /api/v1/auth/register` | No | Create a new user account |
| `POST /api/v1/auth/login` | No | Authenticate and return access and refresh tokens |
| `POST /api/v1/auth/refresh` | No | Exchange refresh token for a new token pair |
| `GET /api/v1/auth/me` | Yes | Return current user profile |
| `POST /api/v1/auth/update-password` | Yes | Change password while logged in |
| `POST /api/v1/auth/forgot-password` | No | Send reset token email if SMTP is configured |
| `POST /api/v1/auth/reset-password` | No | Reset password using reset token |
| `POST /api/v1/analyze/url` | Yes | Analyze and persist an authenticated URL scan |

### 4.1 Authentication

Authentication is implemented with JWT bearer tokens. Passwords are hashed with `passlib` and bcrypt. Token creation and verification are handled in `backend/api/utils/auth_utils.py`.

Unlike the v4 roadmap, the implemented authentication flow includes both access tokens and refresh tokens. The frontend stores:

- `access_token` in `localStorage`.
- `refresh_token` in `localStorage`.
- Serialized user profile in `localStorage`.

The frontend Axios client automatically retries failed authenticated requests after refreshing tokens on HTTP 401 responses.

### 4.2 Database

The backend uses SQLAlchemy and a PostgreSQL database URL loaded from `.env`. The database layer is implemented in `backend/database/database.py` and `backend/database/models.py`. Tables are created on application import through `Base.metadata.create_all(bind=engine)`.

The database models are:

| Model | Purpose |
|---|---|
| `User` | Stores registered user accounts and hashed passwords |
| `Scan` | Stores each authenticated dashboard scan, final verdict, score, reasons, and layer breakdown |
| `Feedback` | Schema for user feedback on scan correctness |

The `Scan` table supports these scan types:

| Scan type | Meaning |
|---|---|
| `url` | Dashboard URL scan |
| `email_text` | Dashboard manually entered email |
| `email_file` | Uploaded `.eml` email |
| `extension_url` | Reserved for extension scans |

In the current implementation, dashboard scans are persisted. The extension URL endpoint is anonymous and does not persist scan records, even though `extension_url` exists in the database enum.

### 4.3 Response Schema and Explainability

The main detection response is `AnalysisResponse`, with:

- `scan_id`: UUID of the persisted scan or generated extension scan.
- `risk_score`: final integer score from 0 to 100.
- `verdict`: `Clean`, `Suspicious`, or `Phishing`.
- `top_reasons`: up to three high-level reasons.
- `layers_list`: individual layer scores, weights, reasons, and optional sub-checks.
- `timestamp`: time of analysis.

Explainability is built into the API because every layer returns both a numeric score and human-readable reasons. The dashboard displays this through a gauge, verdict badge, reason cards, and expandable layer breakdowns.

## 5. Detection Pipeline

The detection orchestration is implemented in `backend/detection/pipeline.py`. The pipeline exposes two main entry points:

- `run_url_pipeline(request: URLRequest)`.
- `run_email_pipeline(request: EmailRequest)`.

Both are asynchronous. Independent detection tasks run concurrently through `asyncio.gather`, which reduces end-to-end latency.

### 5.1 Implemented Ensemble Weights and Thresholds

The actual code uses these layer weights:

| Layer key | Weight |
|---|---:|
| URL layer | 0.40 |
| Email RF | 0.30 |
| NLP | 0.30 |
| Headers | 0.20 |

The ensemble only includes active layers that return a score greater than zero. It redistributes weights over the active layers and computes:

```text
risk_score = round(weighted_average(active_layer_scores) * 100)
```

The implemented verdict thresholds are:

| Risk score | Verdict |
|---:|---|
| `>= 60` | `Phishing` |
| `>= 35` and `< 60` | `Suspicious` |
| `< 35` | `Clean` |

This differs from v4 roadmap thresholds of `>= 70` for phishing and `40-69` for suspicious.

### 5.2 URL Pipeline

The URL pipeline runs:

```text
asyncio.gather(
    analyze_url(request.url),
    analyze_nlp(request.url)
)
```

The URL layer itself runs multiple sub-checks:

| Sub-check | Implementation | Weight | Purpose |
|---|---|---:|---|
| URL RF Model B | `backend/detection/url_analyzer/rf_model.py` | 0.30 | Structural URL/page/infrastructure classification |
| Google Safe Browsing | `google_safe_browsing.py` | 0.40 | Real-time threat intelligence lookup |
| URLhaus | `urlhaus_lookup.py` | 0.25 | Abuse.ch malware/phishing URL reputation lookup |
| WHOIS age | `whois.py` | 0.15 | Domain age risk scoring |

The URL layer normalizes over active sub-checks. Confirmed Google Safe Browsing or URLhaus hits override the layer score to 1.0.

Model B uses this feature vector:

```text
UsingIP, LongURL, ShortURL, Symbol@, PrefixSuffix-, SubDomains,
HTTPS, AnchorURL, LinksInScriptTags, RequestURL, ServerFormHandler,
WebsiteTraffic, AgeofDomain, DomainRegLen, GoogleIndex, DNSRecording
```

Although some comments and roadmap text refer to the server model as "13 features", the actual implemented feature list contains 16 features: 11 Model A features plus 5 Tier 3 features.

Runtime URL feature extraction uses:

- Lexical URL parsing for IP address, URL length, shortener use, `@` symbol, hyphenated domains, and subdomain count.
- Neutral defaults for DOM-style features when page HTML is not available on the backend.
- Tier 3 infrastructure extraction using DNS and WHOIS subprocesses.
- Heuristic calibration for suspicious TLDs, lure tokens, brand tokens, shorteners, young domains, and weak reputation signals.

### 5.3 Email Pipeline

The email pipeline runs:

```text
asyncio.gather(
    analyze_email_rf(request),
    analyze_nlp(subject + body),
    analyze_headers(raw_headers, sender)  # only if raw_headers is provided
)
```

The email pipeline no longer uses the URL model on the sender field. This is the core v4 correction. Email messages are now represented by a dedicated 24-feature Email Random Forest vector.

The email pipeline includes:

| Layer | Implementation | Purpose |
|---|---|---|
| Email RF Model | `backend/detection/email_analyzer/rf_model.py` | Classifies email using text, sender, and header-derived features |
| NLP | `backend/detection/nlp_layer.py` | Scores semantic phishing intent |
| Header Analyzer | `backend/detection/email_analyzer/header_analyzer.py` | Parses SPF, DKIM, DMARC, alignment, and spoofing signals |
| EML Parser | `backend/detection/email_analyzer/eml_parser.py` | Converts uploaded raw `.eml` files into the backend `EmailRequest` schema |

Header analysis only runs when `raw_headers` is supplied. Manual emails without headers are still analyzed through the Email RF and NLP layers.

### 5.4 NLP Layer

The NLP layer is implemented in `backend/detection/nlp_layer.py`. It asks a large language model to return a JSON object with four scores:

| Dimension | Weight |
|---|---:|
| `credential_harvesting` | 0.35 |
| `impersonation` | 0.30 |
| `urgency` | 0.20 |
| `social_engineering` | 0.15 |

The current implementation uses Groq with `llama-3.3-70b-versatile`. This differs from `phishshield-roadmap-v4.md`, which describes OpenAI GPT-4o-mini. The prompt design remains similar: JSON-only output, explicit scoring rubric, counter-examples for false positives, deterministic low temperature, and a 2000-character text limit.

If the Groq API key is missing or the call fails, the NLP layer returns:

```text
score = 0.0
reason = "NLP analysis unavailable"
```

Because the ensemble ignores zero-scored layers, a missing NLP key removes the NLP layer from scoring instead of forcing a neutral value into the average.

### 5.5 Header Analyzer

The header analyzer is deterministic and email-only. It parses:

- `Authentication-Results`.
- `From`.
- `Reply-To`.
- `Return-Path`.
- `Delivered-To`.
- SPF/DKIM/DMARC authentication domains.

It produces risk for:

- SPF failures, soft failures, neutral, missing, or error states.
- DKIM failures or missing signatures.
- DMARC failures or missing results.
- Sender domain and From domain mismatch.
- Reply-To domain mismatch.
- Return-Path mismatch.
- Authentication domain alignment failures.
- Display-name brand spoofing.
- Missing Received chain.

Multiple header signals are combined probabilistically:

```text
combined_score = 1 - product(1 - individual_signal_score)
```

This means multiple moderate failures can compound into a high-risk header result.

## 8. Browser Extension Implementation

The extension is implemented under `extension/` as a Chrome Manifest V3 extension using Vite, React, TypeScript, Tailwind CSS, and `onnxruntime-web`.

### 8.1 Manifest and Permissions

The manifest declares:

| Permission | Purpose |
|---|---|
| `storage` | Store cached analysis results |
| `activeTab` | Work with the active browser tab |
| `scripting` | Support page interaction/injection |
| `tabs` | Listen for tab updates and set tab-specific badges |
| `<all_urls>` | Allow content scripts and analysis across websites |

The extension registers:

- A service worker: `background.js`.
- A content script: `content.js`.
- A popup UI: `index.html`.
- `models/model_a.onnx` as a web-accessible resource.

### 8.2 Extension Analysis Pipeline

When a tab completes loading, `extension/src/background.ts` runs `analyzeTab`.

The extension pipeline is:

1. Ignore non-HTTP/HTTPS URLs.
2. Extract Tier 1 lexical URL features in the service worker.
3. Request Tier 2 DOM features from the content script with a 2-second timeout.
4. Start backend URL analysis in parallel.
5. Merge Tier 1 and Tier 2 features into the 11-feature Model A vector.
6. Run local ONNX inference if `model_a.onnx` is available.
7. Await backend analysis response.
8. Merge local and backend scores.
9. Store the result in `chrome.storage.local`.
10. Update the browser badge.
11. Inject a warning banner for suspicious or phishing verdicts.
12. Notify the popup if it is open.

The extension final score is:

```text
combinedScore = (Model A score * 0.30) + (backend risk_score / 100 * 0.70)
```

The extension verdict thresholds are:

| Combined score | Verdict |
|---:|---|
| `>= 0.70` | `Phishing` |
| `>= 0.40` and `< 0.70` | `Suspicious` |
| `< 0.40` | `Clean` |

### 8.3 Local ONNX Inference

The extension attempts to load `models/model_a.onnx` using `chrome.runtime.getURL()` and ONNX Runtime Web.

The intended input shape is:

```text
[1, 11]
```

The ONNX wrapper expects an input named `float_input` and returns the phishing probability from output index 1.

Current implementation status:

- `ml/models/model_a.onnx` exists and was generated by the URL notebook.
- `extension/public/models/model_a.onnx` is currently missing.
- `extension/public/models/README.md` still says the model is not yet generated.
- If the model is missing, the extension falls back to a neutral local score of 0.5 and still uses the backend result.

Therefore, the extension local model feature is implemented in code and trained in ML artifacts, but not fully wired into the current extension build folder.

### 8.4 Content Script

The content script extracts Tier 2 DOM features:

| Feature | Extraction method |
|---|---|

- Loading state.
- Results panel with score, verdict, and reasons.

The warning banner is injected at the top of suspicious or phishing pages. It displays the verdict, score, top reason, and a dismiss button. The banner escapes reason text before insertion to reduce XSS risk.

## 10. Overall Findings

The current implementation supports several thesis-ready findings.

### 10.1 URL Detection Performance

The URL models achieved high test-set performance:

- Model A achieved 94.97% F1 using only browser-compatible Tier 1+2 features.
- Model B achieved 96.15% F1 using additional Tier 3 server-side features.
- The F1 improvement from server-side features is 1.18 percentage points.

This supports the research claim that privacy-preserving local inference is feasible, but server-side infrastructure signals slightly improve detection.

### 10.2 Email Detection Performance

The Email Random Forest achieved:

- Accuracy: 87.60%.
- Precision: 89.67%.
- Recall: 86.07%.
- F1: 87.83%.
- ROC-AUC: 94.74%.

This indicates that deterministic email features can provide useful phishing classification, especially when combined with NLP and header checks at runtime.

### 10.3 Feature Importance

URL detection was dominated by:

- HTTPS status.
- Anchor link behavior.
- Website traffic.
- Subdomain structure.
- Domain age.

Email detection was dominated by:

- Unique word ratio.
- Word count.
- Body length.
- Total length.
- Digit ratio.
- Suspicious word count.

This suggests that both structural web signals and message-level linguistic/statistical signals are effective for phishing detection.

### 10.4 Explainability

The system is explainable at two levels:

1. Model/training explainability through Random Forest feature importance.
2. Runtime explainability through layer reasons and sub-check breakdowns.

This is important for a user-facing security tool because users need to understand why a page or email was flagged. It is also useful academically because it supports interpretation beyond raw accuracy values.

### 10.5 Hybrid Detection Value

The architecture combines complementary signals:

- Random Forest models capture statistical patterns.
- Reputation APIs catch known malicious URLs.
- WHOIS and DNS signals catch suspicious infrastructure.
- Header analysis catches email authentication and spoofing issues.
- LLM-based NLP catches semantic phishing intent.

This hybrid approach reduces dependence on any single detection technique and makes the system more robust against attacks that evade one layer.

## 11. Limitations

The current implementation has several limitations that should be documented in the thesis.

| Limitation | Explanation |
|---|---|
| Visual analysis not implemented | The roadmap's GPT-4o Vision layer is future work in the current repo |
| Extension Model A not bundled | Local ONNX model exists in ML artifacts but is absent from the extension public model folder |
| Extension scans not persisted | Anonymous extension endpoint does not create scan history records |
| Feedback workflow incomplete | Database model exists but frontend feedback button does not call a backend endpoint |
| Email training dataset lacks real headers | Header-related features are included, but notebook training used empty headers due to dataset limitations |
| Backend URL DOM features are neutral defaults | Backend URL RF does not fetch full page HTML for DOM features, while extension can extract DOM features locally |
| NLP evaluation not separately quantified | The notebooks report RF model metrics; implemented LLM layer was not formally evaluated in saved outputs |
| Runtime external services can fail | Google Safe Browsing, URLhaus, WHOIS, DNS, and Groq are external dependencies |
| Some deployment docs are inconsistent | Roadmap mentions Railway, but current code is configured around Vercel endpoints |

These limitations do not invalidate the implementation. They define the scope of the completed MVP and provide a clear future-work section.

## 12. Suggested Thesis Implementation Narrative

A suitable thesis implementation chapter can describe the system as follows:

PhishShield was implemented as a modular, AI-powered phishing detection system for email and web applications. The implementation was divided into two phases. The first phase focused on offline model development, where URL and email phishing datasets were processed, Random Forest classifiers were trained, evaluated, and exported as runtime artifacts. The second phase focused on software integration, where the trained models were embedded into a FastAPI backend and exposed to users through a React dashboard and Chrome extension.

For URL detection, two Random Forest models were developed. Model A uses 11 browser-safe lexical and DOM features and is intended for privacy-preserving local inference in the browser extension. Model B uses the same features plus five Tier 3 server-side infrastructure features, including website traffic, domain age, registration length, Google index proxy, and DNS recording. The evaluation showed that Model A reached an F1 score of 0.9497, while Model B reached 0.9615. This 1.18 percentage-point improvement quantified the accuracy gain from server-side infrastructure features.

For email detection, a dedicated Email Random Forest model was trained on 82,486 email samples using a 24-feature vector derived from subject, body, sender, and optional raw headers. The model reached 0.8760 accuracy, 0.8967 precision, 0.8607 recall, 0.8783 F1, and 0.9474 ROC-AUC. This model replaced the earlier design flaw of applying a URL classifier to sender email addresses.

The backend combines model outputs with deterministic and LLM-based layers. URL scans run URL RF/reputation analysis and NLP analysis. Email scans run Email RF, NLP, and optional header analysis. Active layer scores are combined using a weighted ensemble and converted into a final Clean, Suspicious, or Phishing verdict. Each response includes human-readable reasons and per-layer scores to support explainability.

The dashboard provides authenticated scanning, scan history, and account management. The Chrome extension monitors loaded web pages, extracts local URL and DOM features, attempts ONNX inference, calls the backend, merges local and server scores, and warns the user through a badge and injected banner. This demonstrates how the same detection architecture can serve both explicit user-submitted scans and real-time browser protection.

## 14. Conclusion

The implemented PhishShield system is a functioning multi-layer phishing detection platform with a strong ML foundation and practical user interfaces. The offline training results show high URL detection performance and useful email detection performance. The application integrates these models into a backend ensemble with explainable outputs, authenticated dashboard workflows, and an extension-based URL warning mechanism.

The major implementation change from the roadmap is the correction of email analysis through a dedicated Email Random Forest model. The major incomplete roadmap items are visual analysis, operational feedback collection, authenticated extension persistence, and bundling the local extension ONNX model into the extension public model directory.

For the thesis, the strongest defensible narrative is that PhishShield demonstrates a hybrid AI system combining task-specific Random Forest classifiers, LLM-based semantic analysis, deterministic security checks, and explainable ensemble scoring for phishing detection across both email and web application contexts.
